# Personal data cleanup

Local contact history, campaign/template removal and separate single-owner installation retirement—not Simbi deletion/integration, a legal retention recommendation, anonymization or secure erasure. Never use cleanup to conceal an uncertain provider action or bypass an opt-out.

## Operator procedure

1. Sign in as the local **owner** and open **Settings → Privacy & cleanup**. Admin/editor/viewer roles cannot perform cleanup. Export workspace JSON first if you need a readable copy; JSON cannot be restored through the app.
2. Optionally save **Keep inactive contact history for (days)**: 30–3650 days. This is your preference, not a legal rule or automatic purge. Initial setup uses `SIMBI_RETENTION_DAYS`; later changes belong to this workspace. The CLI's analytics/session cleanup continues using the environment setting.
3. Choose **Old, closed contact history**, **One selected contact and all its local history**, **One campaign and its conversation history** or **One reusable template; keep its drafts**. Named selections support name search and pages of50. A failed search is not an empty result; switching scope clears the previous search/selection/preview.
4. Click **Preview cleanup**. Read the exact names and removal counts for contacts, campaigns/templates, drafts, handoffs, replies and linked reminders. Campaign previews also list/count contacts retained as do-not-contact; template previews count links cleared separately from drafts removed. Age-based previews show their fixed cutoff and this scan page's checked/protected/oversized/selected/remaining figures, never workspace totals. Preview/cancel does not delete operational records.
5. Click **Review removal**, check the explicit acknowledgement and enter your **local app password**, not a provider password. Cancel/Escape removes nothing; reopening clears password/acknowledgement. Pending requests disable repeat submission and closing.
6. A verified SQLite recovery copy must succeed before deletion. Backup failure removes nothing. Success shows a timestamp, scope-specific contact/campaign/template count and recovery filename. Keep the file private in `SIMBI_BACKUP_PATH`; standalone Windows uses its normal per-user runtime configuration.
7. If a response is interrupted or its receipt cannot be verified, do not assume failure. The browser validates the same kind, plan ID, every previewed count, a backup basename, timestamp and replay flag before showing completion. Keep and retry **the same preview** with fresh acknowledgement/password to retrieve its receipt without repeating removal. Cancel and attempted confirmation clear password/acknowledgement. **Keep the displayed Cleanup reference before closing this page.** After refresh, **Check cleanup receipts** shows this owner's last ten validated completed plans; **Find cleanup receipt by reference** retrieves an older completion by that exact32-hex reference, without a new confirmation or deletion. Lookup validates the returned reference and receipt shape and leaves any current preview intact. Absence from the last-ten list or a404 lookup is not proof of failure: the reference might be wrong, pending, replaced or unavailable to this current owner/workspace. Do not start a replacement destructive batch on that basis. If the reference is lost, inspect the owner-visible audit log for `privacy.cleanup_completed` and its opaque entity ID/time/counts, or obtain read-only local operator support to inspect completion metadata. Do not reset/restore/delete the database to guess the outcome. A recovery file alone is not completion evidence. A malformed receipt list is an error, not invented completion counts.
8. Expired, replaced or changed previews must be generated and reviewed again. Never substitute a freshly computed batch for one already confirmed.
9. In **Old, closed contact history**, process the selected batch of at most50, then use **Preview cleanup** again on the same scan cursor until no eligible contacts are selected. The remaining figure (`remaining_eligible_contacts`) counts eligible contacts in that observed page not selected in this batch; it excludes protected contacts. If the page has more contacts, **Next contact scan page** becomes available only when that preview selects none; it scans IDs after the displayed page boundary. The first page can contain only protected recent contacts while later pages contain eligible old contacts. Continue until no more pages remain. Counts and eligibility describe each observed page, not a frozen global snapshot. **Restart contact scan** starts at ID0; saving a retention preference or switching scope also restarts. After changes to earlier contacts, additions with reused lower SQLite IDs, reload or restore, start again to recheck earlier IDs. No eligible contacts on one page is not proof that the workspace contains no old/private data.

## Exact policy and retained data

Keyed reminder creation also keeps minimized retry-reference tombstones: workspace/actor IDs, fingerprints, creation time and a nullable reminder link, not another title/body/due-date copy. Contact/campaign removal clears links to removed reminders but preserves these tombstones so an old request cannot recreate deleted history. They remain in complete database backups, are omitted from workspace JSON exports and redacted support content, and are counted/removed by personal retirement. They are not anonymous data or secure erasure. See [the exact replay/restore limits](REQUEST_RECOVERY.md#durable-reminder-creation-receipts).

The separate core-creation ledger keeps similarly minimized scoped fingerprints and typed nullable links for campaigns, contacts, templates, drafts, replies and committed CSV-import audit history. Removing target records clears links but preserves tombstones; replay cannot recreate them. CSV recovery returns original import-audit counts without reimporting contacts removed or changed later. Cleanup preserves audit history and these references; explicit personal retirement counts/removes both ledgers (20 operational tables). Full SQLite backups/restores preserve them, while JSON exports/redacted support omit them. Neither ledger is anonymous data, durable browser working-copy storage or secure erasure. See [core recovery and historical-count limits](REQUEST_RECOVERY.md#durable-core-creation-confirmations).

Contact/age-based removal deletes selected prospect rows. Foreign-key cascades remove their drafts, handoffs, replies and directly/indirectly linked reminders. Campaign descriptions, templates, unrelated contacts/history, account data, audit history, analytics, provider settings, HAI files, exports and other backups are not removed.

Campaign removal deletes the selected campaign plus its drafts, handoffs, replies and draft-linked reminders. Contact rows, contact-only reminders, templates and other campaigns/conversations remain. Every affected provider/source identity receives or retains a do-not-contact restriction, even when other campaigns still have drafts for it: deleting outreach evidence must not defeat cooldown/repeat-contact protection. Existing restriction reasons remain unchanged. The contact's stored consent field is not rewritten; the suppression registry is authoritative at intake/review/handoff. Campaign removal refuses pending/uncertain actions for any affected contact, including those in another campaign. It does not require a particular age or archived status.

Template removal deletes the reusable template and sets its existing drafts' `template_id` to null. Draft bodies/subjects, states, approval timestamps, prepared content hashes, handoffs, replies, reminders and contacts remain unchanged. This is safe during a pending handoff because the exact approved draft text is not modified. It does not remove the template text already copied into drafts; remove those contacts/campaigns separately if appropriate.

Campaign/template previews inspect linked histories for ownership, uncertainty and stale changes. More than1000 root-linked drafts or inspected related rows returns `privacy_scan_limit`, not an incomplete success. The row count includes related conversation/campaign/audit records; the complete suppression registry is streamed separately into its digest, not counted/copied into each graph. No schema migration or dependency change is needed for these scopes; the immutable migration003 plan format already stores kind and IDs. Empty campaigns/templates can be removed after the same preview/password/backup gates. Foreign targets remain404; inconsistent cross-workspace cascades fail closed.

Every removed contact retains a canonical provider/source identity in the suppression registry. New tombstones say `Local history removed; do not contact`; existing restrictions/reasons are preserved. Linked suppression prospect IDs become null. Recreating/importing that identity is still opted out: removal must not erase duplicate/cooldown evidence and allow renewed outreach. Retained source identifiers and potentially identifying historical audit/suppression text mean this is **not complete anonymization or secure erasure**. No restriction-release workflow is added.

Age-based scans inspect at most1000 contacts of every age per explicit ID-cursor page, select at most50 eligible contacts, and report exact page-only protected/oversized/remaining counts plus continuation. Selection does not depend on lexically sorting timestamp strings: valid time-zone-aware activity is checked semantically. Empty/missing required creation dates, invalid dates, missing time zones, recent activity, non-archived linked campaigns, open reminders and prepared/opened/ambiguous handoffs protect contacts. Ambiguous/handoff-created drafts are protected even with inconsistent handoff links. Contacts without conversations can qualify when their own history is old. Only displayed, fixed IDs can be removed; new contacts are not added to an existing confirmation. Templates/campaigns remain.

Each inspected contact graph is bounded to1000 rows across the contact, conversations, campaigns and record-specific audit activity, with SQL limits before materialization. Oversized or inconsistent histories remain protected during age-based scanning, so one large graph does not hide later contacts. Explicit named-contact removal fails closed for an oversized graph rather than partially deleting it. Existing campaign/template combined-history bounds remain. A large workspace suppression registry does not make an otherwise small graph oversized: its complete workspace-scoped contents are streamed into one digest per snapshot instead of copied into every contact graph. Registry changes still invalidate pending confirmation. No private registry content is duplicated into plan metadata.

Individual removal does not require old age or archived campaigns and includes linked reminders, as shown in the preview. It still refuses pending/uncertain handoffs: resolve the actual outcome first. Inconsistent cross-workspace references or invalid stored source URLs fail closed instead of cascading into another workspace.

## Safety and recovery contract

- Immutable migration `003_privacy_cleanup.sql` adds owner/workspace-bound plans/receipts without rewriting existing records. Plans store IDs/counts/cutoff/content digest, not duplicate names, notes, messages or passwords.
- Previews last ten minutes. A new preview invalidates that owner's older pending previews, including other tabs. Relevant content/state/links, suppression registry and retention preference are rechecked under a writer transaction.
- Current session, membership and owner role are rechecked inside that transaction. Confirmation requires CSRF, password verification and acknowledgement. Failed reauthentication is throttled separately from sign-in attempts. Clients cannot add target IDs/counts/content or use another owner's/workspace's plan.
- Before writer reservation, confirmation acquires the same nonblocking maintenance-operation lease used by managed worker/HAI export and audit minimization. A busy lease returns409 without backup/deletion; retry the same preview after the operation finishes, or renew it if records changed. This prevents managed export from racing across cleanup, but does not delete an already published/ingested external copy. The transaction then reserves SQLite's writer lock. A separate reader copies and integrity-checks the committed pre-cleanup database. Deletion, new suppression identities, receipt and non-content audit summary commit together; database errors roll them back. A recovery copy may remain after failure and is not itself proof of successful removal.
- Completed-plan retry returns its stored receipt without a second backup/audit/deletion. Newly added contacts are never silently included. Filesystem administrators can still modify SQLite; cryptographic audit integrity is not claimed.
- Recovery copies include all database records, local password hashes and sessions for all workspaces—not redacted support data. Existing worker backup-pruning rules apply in the backup folder; make a separately protected copy if longer retention is needed.
- Use the existing offline, backup-first restore procedure, testing on an isolated installation first. Full restore can resurrect removed data, old passwords/sessions and older suppression/safety state. Reconcile restrictions/outcomes before resuming. Never silently restore the real installation during a test.

Implementation follows [SQLite transaction semantics](https://www.sqlite.org/lang_transaction.html) and the [Python SQLite backup API](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup). Actual isolated SQLite tests check the writer lock, snapshot contents and rollback, not only these documents.

Exactly one matching ID for named scopes; no IDs for retention. Returns kind, opaque plan ID, expiry, cutoff, contacts/records/counts, affected retained contacts and batch figures. |

Retention responses add `after_id`, `scanned_contacts`, `oversized_contacts`, `has_more_contacts`, and nullable `next_after_id`; existing protected/remaining counts are page-only. Cursor never supplies deletion IDs. |
| `POST /api/privacy/confirm` | Owner + CSRF + fresh password; `{ "plan_id": "opaque32hex", "current_password": "local password", "confirmed": true }`; returns completion receipt/backup basename. |
| `GET /api/privacy/receipts` | Current owner; last ten completed receipts for this owner/workspace, no message content. |
| `GET /api/privacy/receipts/{plan_id}` | Current owner; exact completed receipt for this owner/workspace, including older receipts outside the last ten. Strict32-lowercase-hex reference; pending/invalid/unknown/foreign reference returns indistinguishable404 `privacy_receipt_not_found`. Read-only outcome lookup, no password confirmation, backup, deletion or new audit event. The reference alone grants no public access or write authority. |
| `DELETE /api/prospects/{id}` | Deprecated bypass: existing owned contact returns `409 privacy_preview_required`; foreign contacts remain `404`. Use the two-step privacy contract. |

Strict bodies reject extra fields. Wrong password/role/CSRF: 403; throttling: 429. Expired/replaced/stale/empty/protected/oversized plans or busy managed maintenance: structured409. Invalid selection/body: 422. Backup failure: `503 privacy_backup_failed`, no deletion. Network interruption is not an operation result: use retry/receipts. New snapshot digests avoid duplicating the registry; an uncompleted preview from an older app version may therefore require renewal after upgrade. Completed receipts remain replayable and no migration or automatic data cleanup is performed.

## Personal installation retirement

Use this only to stop using the entire local personal installation, not to reset outreach restrictions or delete a Simbi account.

1. As the owner, enable **Settings → Emergency safety stop**. Resolve every prepared/opened/ambiguous handoff and every ambiguous/handoff-created draft. Retirement refuses these states, including orphan draft uncertainty. Exactly one user, one owner membership and one workspace must exist; it never deletes other local members/workspaces to make itself eligible.
2. Open **Retire personal installation → Preview personal retirement**. Review the exact owner/workspace names and counts for all18 account/workspace/authentication/history tables. Names are returned to the browser, not copied into stored plan metadata. Counts include the preview audit event and the plan itself, which will also be removed. More than100,000 scanned rows, invalid foreign keys or unknown schema objects/tables fail closed. The plan lasts ten minutes; a new preview replaces pending previews.
3. Choose **Review personal retirement**. Read both warnings; acknowledge the exact deletion and loss of do-not-contact history, type `RETIRE`, and enter the current local password. Cancel/Escape clears credentials/checks without deleting data. The preview itself writes only plan/audit metadata. Closing and repeat submission are blocked while a request is pending.
4. Confirmation rechecks owner/session, role, CSRF, password throttling, sole-owner eligibility, safety stop, schema, uncertainty and a digest of all account/workspace records. Changes, including sessions/restrictions/settings/audits, require a fresh preview. A wrong password creates a sign-in protection record, so obtain a new preview before the next confirmation; this does not reset throttling.
5. Before any deletion write, a separate reader creates an integrity/foreign-key checked SQLite backup while the writer is reserved. Failure leaves the live installation unchanged. The backup contains the **paused** workspace, previous password hash/sessions, content, restrictions and pending preview. It is private recovery material. Database errors after backup roll back deletion and marker together; an existing backup alone does not prove completion.
6. On completion the account, workspace, memberships, sessions, campaigns, contacts, templates, drafts, handoffs, replies, reminders, restrictions, provider/feature settings, audit/analytics, login-attempt hashes and cleanup plans/receipts are removed from the active database. A singleton retirement marker holds only counts, completion time, opaque plan ID and backup basename. Schema-migration history and non-content maintenance metadata remain. This is not byte-level database/WAL erasure.
7. The completing tab shows the receipt and removes private views. Other app tabs receive an ephemeral `retired` notice and verify the public status before changing screens; no content or token is broadcast. Restricted/unsupported browsers detect retirement on reload. Cookies are cleared, old sessions are invalid, and new setup/login remain blocked across restart. There is no reset/reopen endpoint.
8. If the response is interrupted, the browser looks up the **same** opaque128-bit preview token's read-only completion receipt; success is shown only for a matching kind/ID/counts/timestamp/backup basename. If no verified receipt is available, use **Check completion receipt** and do not assume failure or submit a new destructive plan. **Keep the original page open until its receipt is recovered.** The token remains in current-page memory only; it is not saved in localStorage, so closing/reloading loses it and the detailed receipt display. Reload still shows the public retired state without receipt identifiers/content if retirement completed. If the token is lost, use local operator support to inspect the minimal retirement marker and protected recovery copy; never reset/delete the database or infer failure from an interrupted response. An apparently active state while a request is still outstanding is not final failure proof. Receipt URLs may appear in access logs, so protect them; they grant no write/sign-in authority.

Managed worker/HAI export and retirement share a nonblocking operation lease, acquired before database writer reservation. A busy operation returns503 without changing records; retry the same preview after it finishes, or renew it if maintenance changed records. Retired workers no longer generate reminders, purge authentication records, create/prune backups or refresh HAI; non-content health timestamps may continue. Manual HAI export cannot publish a stale pre-retirement payload across the same managed lease. Unmanaged external tools are not controlled.

**External copies are unchanged.** Simbi, backups, workspace exports, browser downloads, existing HAI files and already ingested HAI content may still contain private data. Protect/remove those separately with the appropriate authority. The app deliberately does not silently delete external files or receiving-side records. Offline restore of the protected pre-retirement backup restores the paused workspace, prior credentials/sessions and restriction history. Stop app/worker first and verify restoration against a separate target; reconcile restrictions/outcomes before resuming. JSON exports cannot restore the installation. Do not create a new empty database to bypass lost opt-outs.

Follow the [separate-target restore example](../README.md#test-a-restore-without-replacing-the-real-database): a new temporary PowerShell window selects a uniquely named test database using `SIMBI_DATABASE_PATH` before calling restore. Verify that printed target, keep its private copy protected, and close the temporary window afterwards. The ordinary restore command without these test overrides operates on the configured installation; do not use it as an assumed safe test.
