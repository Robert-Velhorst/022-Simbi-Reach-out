# Interrupted requests and unverified results

## For the personal operator

The application waits for a complete JSON response, not just a connection or response headers. Its 20-second request deadline includes reading the response body. An empty, broken, HTML, truncated or primitive JSON response is not accepted as a successful API result. A read failure is displayed as an error, not an invented empty collection.

For a write, **an interrupted response does not prove that the change failed**. The server may have saved it before the connection broke. The English warning says: “The request outcome is not confirmed.” The Dutch warning says: “De uitkomst van het verzoek is niet bevestigd.” Both tell you that local records may already have changed and to check their current state before trying again. The client never automatically retries a write.

Campaign, prospect, CSV import, template, draft preparation, reply and reminder forms refuse repeated submission while pending. Their inputs, Cancel and Close are disabled; Escape and backdrop dismissal cannot discard the pending form. A translated notice explains the wait. The form itself remains keyboard reachable for scrolling even when every input is disabled. After an unverified response, the open form retains its entered values and enables controls for a deliberate next decision.

Pending focus remains in the form only when the document is foreground and focus was inside that form or fell to the page body; another control/window's focus is not reclaimed. Actual Tab re-enters remaining native-dialog controls when the former active control is disabled. Non-form row actions remember their active control for the existing foreground/lost-body-only post-enable restoration. These are keyboard safety measures, not automatic write/navigation replay.

First try the action-specific same-reference recovery below while the page remains mounted. **Do not browser-reload or navigate away first: that can destroy the unresolved reference and entered values.** An in-page record refresh is different from a browser reload, but check that it does not replace your form/page before using it. Keep a private copy if necessary and close only when ready. If you have already lost the reference or intentionally choose to leave, inspect saved records before creating another: for a template, check the authored text, not just its name; for CSV, inspect the relevant contacts. This is temporary in-memory retention, not autosave, server-wide generic duplicate protection or crash recovery. Other actions must be checked in their own record view; not every action has the same recovery controls. Wider route/reload/closure protection for these creation forms remains open; the separate unresolved-draft editor has its own leave guard.

After the same-reference choice above, check uncertain campaigns in **Campaigns** (name, purpose and limits), contacts/imports in **Prospects** (name and source URL), and prepared drafts in **Review queue** (the selected contact/campaign/template and rendered text). Check recorded replies in **Replies** (conversation and text) and reminders in **Reminders** (conversation, title and due time). If you choose to reload/navigate, expect the current form/reference to be lost. Absence from one page or from the open-reminder view is not proof that no write occurred. If you cannot establish whether the matching record exists, stop repeating the creation and investigate with redacted diagnostics or a maintainer. Do not send a message, invent a sent outcome or disclose private exports to resolve a local uncertainty.

Use the existing action-specific recovery paths where available:

- Campaign/contact/template creation, draft preparation, replies and committed CSV imports now each supply their own random retry reference. After an uncertain save, retry the original values in that page to recover the same attempt. No automatic retry occurs. A matching confirmed result ends the attempt; changing values under a committed reference does not create something else. Cancel clears the form fields, not its unresolved reference. The reference remains only while that page component is mounted: navigation, reload, sign-out, crash or closure can lose it. Re-enter the original values after Cancel; after losing the reference, inspect saved records before creating again. Contact creation and CSV import have separate references. An uncertain reply can still select a conversation now marked “replied” for recovery; this is not permission to record a second reply. CSV recovery reports the original import counts, not the contacts currently present.
- Reminder creation: the current form supplies a random retry reference. After an uncertain result, retry the original conversation, title and due time in that same page; no automatic retry occurs. A confirmed same-reference replay closes the form without creating another reminder or audit event. Changed values under a committed reference are refused. Completed, changed or removed reminders are not reopened or recreated. The reference survives Cancel/reopen while the Reminders page remains mounted, but navigation, reload, sign-out, crash or closure can lose it and the form values. The warning displays the reference and this boundary. After losing it, inspect saved reminders before creating again; the open view alone is not proof of absence. This is not autosave or cross-tab duplicate detection.
- Draft saves: [compare the current saved version](DRAFT_SAVING.md), preserving your working text and requiring a separate explicit save when appropriate.
- Handoffs: retain the same request identity and inspect the persisted handoff. Preparing/recovering one is not sending on Simbi or proof of delivery.
- Local cleanup and audit minimization: keep the exact preview/reference, inspect its completion receipt, and follow [cleanup recovery](PRIVACY_CLEANUP.md) or [audit minimization](AUDIT_PRIVACY.md). Do not replace an uncertain removal with a new preview simply because its response was lost.
- Personal retirement: the existing read-only completion-receipt lookup can recover a completed retirement after its confirmation response becomes unreadable. Success still requires the matching verified receipt; absence is not proof that retirement failed.

A cancelled request is separate from a timeout. Cancellation before dispatch starts no request. Cancellation or timeout after dispatch does not undo a server commit. Structured4xx refusals retain their specific explanation. For5xx write failures, only the inspected pre-change recovery-backup and retirement-maintenance refusals retain their specific explanation; other5xx errors remain uncertain even when their JSON is readable.

## Developer boundary

`frontend/src/api.ts` owns one AbortController, a deadline covering fetch plus JSON consumption, and a bounded rejection race. It removes the caller's abort listener and clears the timer on every settled exit. Caller cancellation uses `request_cancelled`; timeout uses `request_timeout`; network failure keeps `network_unavailable`; an unreadable successful response or non-object/non-array top-level JSON uses `response_unverified`. HTTP failures retain valid string codes, with `request_failed` fallback for malformed fields. Read/4xx errors retain valid messages;5xx write errors use the uncertainty warning except the two inspected pre-change refusals below. Raw unreadable response bodies/parser errors are not retained in these errors.

The wrapper accepts only non-null JSON objects/arrays as the current API's top-level success shape. `coreResponse.ts` additionally validates seven POST contracts: campaigns, prospects, templates, draft preparation, replies, reminders and CSV preview/commit. Campaign/prospect/template confirmations require positive safe integer IDs, bounded fields and inspected server-normalized submitted values; an existing stronger prospect opt-out is allowed. Draft preparation checks its ID, review state, score/flags and exact submitted campaign/prospect/template IDs. Reply checks the exact conversation, trimmed submitted text and a valid received instant; an explicitly supplied received instant must match including microseconds. Reminder checks both nullable targets, trimmed title and exact due instant including microseconds. Draft, reply and reminder confirmation fields are read from the actual inserted records inside their authenticated transactions. A keyed reminder response must additionally match the current creation_key and contain a boolean replayed. A server-assigned reply time is not independently checked against the browser clock, and rendered draft content is not independently validated by this creation contract. Before a transaction, the backend rejects non-positive/unsafe/coerced creation IDs and invalid calendar/timezone-free supplied timestamps. Supplied instants require seconds and at most six fractional digits and normalize to UTC; old history is not rewritten. Deploy matching frontend/backend: newer clients reject older minimal confirmations as unverified after a possible commit. CSV checks stage, bounded counts/errors and commit-count consistency before advancing. `usePage` checks list shape, safe counts, exact requested offset/limit and item-count bounds while preserving its generation/unmount/last-result safeguards; it does not validate every row's fields.

**This is not a complete per-endpoint schema validator.** Other readable objects can still contain missing, wrong or stale fields. Draft version checks and privacy/audit/retirement receipt checks remain necessary, and wider semantic validation remains open. Do not add empty-body/204/primitive-returning endpoints without explicitly revising and testing this contract. The two5xx refusal codes are `privacy_backup_failed` and `retirement_maintenance_busy`, whose backend guards occur before the requested change. Do not expand that exception without inspecting the actual transaction/commit boundary.

Local cleanup, audit minimization and personal retirement treat `response_unverified` and cancellation as potentially interrupted outcomes. Retirement retains its opaque preview-token recovery: this token can retrieve only the non-content completion receipt, not private records or account access. Its existing authentication, CSRF, maintenance and provider boundaries remain. No automatic retry, private browser storage, dependency or provider operation is added. The reminder-specific additive schema/contract follows.

### Durable reminder creation receipts

`POST /api/reminders` optionally accepts exactly one `Idempotency-Key`: 16–120 ASCII letters, digits, underscores or hyphens, without whitespace or punctuation. Callers must generate an opaque high-entropy reference (the UI uses `crypto.randomUUID()`), retain it for the logical attempt and not log private payloads. Missing keys preserve the legacy API response and creation behavior **without replay protection**. Invalid or repeated header values are rejected before writes. The header is not a login capability.

Migration005 adds `reminder_creation_receipts`; migrations001–004 are unchanged. In the same `BEGIN IMMEDIATE` transaction, the route rechecks the live session/current membership and write role, looks up the workspace-and-actor-scoped key fingerprint, creates the reminder/audit event if new and saves the receipt. Concurrent same-key writers serialize. A receipt failure rolls the reminder and audit back. Only after commit is the confirmation returned. The UI also requires matching `creation_key` and a boolean `replayed` alongside the existing target/title/due/status checks; a matching row without the right receipt remains uncertain.

The receipt stores workspace/actor IDs, SHA-256 of the opaque key, HMAC-SHA-256 fingerprints of normalized submitted values and the entire original reminder row, a nullable reminder link and creation time. It does **not** store the raw key, title, due date, submitted target IDs or another JSON response/body copy. This is minimized metadata, not anonymous data. HMAC confidentiality depends on a high-entropy caller key; it is not encryption or secure erasure. Response text comes from the authenticated current reminder row, not a retained private response cache.

An unchanged, existing reminder with the same normalized request returns the same ID/confirmation and `replayed:true`, with no new reminder, audit entry or receipt update. Equivalent UTC offsets and trimmed titles normalize identically. A changed request returns409 `reminder_key_conflict`; a deleted or changed row returns409 `reminder_receipt_unavailable`. Its nullable foreign key becomes null on deletion, retaining the tombstone even if SQLite reuses that numerical record ID. Workspace-link triggers refuse cross-workspace receipt references. The receipt is not an approval or send outcome.

There is no automatic receipt expiry or pruning. At10,000 references per workspace/actor, new keyed creations are refused with409 `reminder_receipt_limit`; existing references still work. Contact/campaign cleanup preserves these minimal tombstones and clears links to deleted reminders; retirement counts/removes them. They are included in complete database backups/restores, but not workspace JSON exports or redacted support content. A JSON export is not a restoreable retry ledger. Restoring an older backup can lose newer receipts; it cannot guarantee deduplication of post-backup attempts. Current migration validation/retirement eligibility recognize the additional table. No owner database was migrated during implementation.

This reminder protection is for the same key, actor and workspace—not identical text under a new key, another tab/user's fresh request, worker reminders or reminder status changes. The other six creation/import routes have the separate ledger below. The browser retains only its current opaque reference in component memory; the server receipt persists in SQLite. Do not describe this as universal idempotency, durable browser recovery or exactly-once provider delivery.

### Durable core creation confirmations

Migration006 adds `core_creation_receipts` without modifying migrations001–005 or copying operational content. The existing migration005 reminder ledger remains separate. Optional `Idempotency-Key` headers apply to `POST /api/campaigns`, `/api/prospects`, `/api/templates`, `/api/drafts`, `/api/replies` and `/api/prospects/import` with `commit:true`. The exact-one-header, 16–120-character ASCII grammar and high-entropy caller requirement are the same as for reminders. Invalid/repeated core headers return400 `creation_key_invalid` before writes. Missing headers preserve legacy response shapes and behavior **without recovery protection**. CSV preview remains read-only, does not consume a reference and does not return receipt fields, even if a caller supplies a header.

These six operations share a key namespace scoped to workspace and actor: reusing a committed reference for another operation or different normalized input returns409 `creation_key_conflict`. Normalization includes validated model defaults/trimmed strings, lowercase provider/validated source URL, canonical explicit reply timestamps and the ordered validated CSV rows rather than raw CSV formatting or ignored columns. A missing/null reply timestamp remains the same logical input, so a retry recovers the original server-chosen time. Reference reuse before any successful commit is not persisted; an invalid or rolled-back request did not reserve the key.

The route rechecks the live session, current membership and write role within the same `BEGIN IMMEDIATE` writer transaction as lookup/creation. Normal CSRF, ownership and operation validation remain required. A matching unchanged record returns the original confirmation with the supplied `creation_key` and boolean `replayed:true`; a new keyed commit returns `replayed:false`. No additional record, audit event or receipt update occurs on replay. All first-attempt side effects commit together: creation, audit, receipt, reply state/reminder cancellation and CSV intake do-not-contact changes. A receipt failure rolls back those changes. The frontend requires matching receipt fields **and** its existing record/target/text/state/time/count confirmation checks before closing a form or rotating the reference.

The ledger stores workspace/actor IDs, the key's SHA-256, operation, keyed HMAC-SHA-256 of normalized input and the complete original target row, one nullable typed target link and creation time. It does not store raw keys, private input/output text, CSV rows or another response/body cache. This metadata is minimized, not anonymous or encrypted; confidentiality of content fingerprints depends on a high-entropy key. Campaign/prospect/template/draft/reply confirmations are reconstructed from their unchanged authenticated rows. Row changes (including draft review/edit/state changes) or deletion return409 `creation_receipt_unavailable`, not a stale creation result. Nullable foreign keys keep tombstones when targets are deleted, even if SQLite later reuses the ID. Workspace and operation/link constraints reject inconsistent references.

CSV receipts instead link to the existing `prospect.imported` audit event whose non-content details store inserted/duplicate counts. A replay returns those **historical completion counts**, not current-inventory counts or proof that every imported contact is still present or unchanged. Removing or changing imported contacts does not rerun the import or its restrictions. Changing/removing the linked import audit event makes recovery unavailable. Imported rows themselves are not copied into the receipt. This deliberate distinction prevents an old import retry from recreating removed contacts.

At10,000 core references per workspace/actor across these six operations, new keyed creations fail with409 `creation_receipt_limit`; existing recoveries still work. There is no expiry or automatic pruning. This is separate from the reminder ledger's10,000-reference limit. Personal cleanup preserves minimal tombstones/clears deleted links; explicit personal retirement counts/removes both ledgers (now20 operational tables). Complete SQLite backups/restores preserve both; JSON exports and redacted support bundles omit them. Restoring a legacy five-migration backup adds the empty new ledger while preserving old rows; restoring an older backup can lose later confirmations, so post-backup attempts are not guaranteed deduplicated. For rollback to an older release, use its complete pre-upgrade backup—do not remove a live receipt table or rewrite immutable migration history.

No private working-copy storage, automatic retry, provider integration or authentication bypass is introduced. New keys, another actor/workspace, navigation/reload-lost references, worker actions, updates, approvals, sends and handoff/cleanup/retirement-specific receipts are outside this core confirmation contract. A recovered creation is not a fresh approval, provider delivery proof or global exactly-once guarantee. No owner database was migrated during implementation.

## Verification and limits

Fifteen shared-response regressions and two English/Dutch actual-template-form regressions demonstrated the original failures before the fix. Two further retirement regressions require unreadable/null confirmation recovery via one read-only exact receipt request. Four additional cases distinguish arbitrary/internal5xx envelopes from the two inspected pre-change refusal codes. Existing structured-rejection, handoff-identity, last-result generation and privacy/backup behavior remain tested. The two generic resource fixtures now use object-shaped API records while retaining all stale-response/unmount assertions. Old handoff/compliance/cleanup-preview/stop-contact tests now expect truthful uncertainty wording for interrupted or arbitrary503 writes while retaining same-key replay, explicit-retry choices, no-fake-empty-preview and retained-reason/focus assertions.

`scripts/e2e-api-response.mjs`, appended to the existing full engine workflow, starts an owned fictional database/backend and an ephemeral loopback response proxy. It forwards real writes before substituting malformed, held empty-object or mismatched-content confirmations. Held responses require disabled controls, actual repeated Enter/Escape refusal, keyboard-reachable scrolling and authenticated readback of one stored template before release. JSON whitespace starts the held body because Firefox's observer does not report header-only delivery; it remains incomplete until explicit release. Native short-name validation must dispatch zero writes. Separate unfinished bodies exercise the English desktop read/Dutch mobile write 20-second deadline and connection closure. Both languages reject malformed and wrong-page reads without claiming emptiness, then recover through explicit read retry. Nine selected scans per engine (EN four/NL five) supplement, not replace, the retained full suites; distinct scenarios create EN three/NL four templates, exactly one per title.

The core follow-up adds 29 contract tests, three pagination tests and 15 pending-form cases: seven forms in both languages plus a held CSV preview/commit transaction. Consecutive same-render submits must dispatch once, cancellation must retain the dialog, and an unverified result must retain inputs. Native field bounds mirror inspected backend model limits; server validation remains authoritative. Exact completed counts, engines, failures and publication revisions belong in the ledger, not these test targets.

The helper uses sequential keyboard controls, 1440×1000 English desktop and 390×844 Dutch mobile, external-request blocking, identity/nonblank/overlay/overflow checks, console monitoring and screenshots outside the repository. A long mobile error form scrolls: Tab to an action and use End to reveal the bottom row; both complete buttons must fit before the separate action-row screenshot and cancellation. Firefox can leave a focused button partly below the viewport, so focus alone is not visibility proof. It never opens or writes to Simbi. A failed initial helper expected POST200 instead of the real POST201; that was a fixture diagnostic, not an application failure or accepted run. Only completed runs tied to the exact revision count as acceptance; see [the current ledger](PRODUCTION_READINESS.md).

This boundary is not generic write idempotency, complete form validation, durable working-copy storage, secure erasure, assistive-device certification, authenticated Simbi acceptance, or proof of Robert's installed runtime. Those remain separate personal-production gates.
