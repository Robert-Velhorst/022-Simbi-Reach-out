## Using the personal application

On a signed-in page, the first Tab reveals **Skip to main content** (**Ga direct naar de hoofdinhoud** in Dutch). Enter moves focus directly to the named main region without changing the route or records. Selecting a navigation link moves focus to that page's content, including selecting the current route. Page headings identify the destination; loading and error messages remain truthful while records are fetched.

At widths of 980 CSS pixels or less, the desktop sidebar is hidden, not merely moved offscreen. Tab to **Open navigation** (**Navigatie openen**) and press Enter or Space. The named native dialog opens with focus on **Close**. Tab/Shift+Tab cycle through its close control, ten primary routes, Help and Sign out; the underlying page is inert while it is open. Escape, Close or clicking the backdrop dismisses navigation and restores its trigger. Selecting a route closes it and focuses the main region instead. Switching to desktop width closes the drawer and focuses content; an invisible drawer cannot keep the desktop page blocked.

The drawer scrolls in a short viewport. Focusing its last control brings that control into view. **Sign out is an account action**, not a navigation demonstration: activate it only when you intend to end the local session. Help is available inside mobile navigation as well as the desktop header. The language selector is outside the modal; close navigation before changing it, or use another tab's existing language preference workflow.

Populated dashboard queue, prospects, reports and audit tables are named, keyboard-focusable regions with native table headers. Tab to the table region and use Left/Right arrow keys to reveal overflowing columns. The scroll stays inside the table rather than widening the page. Keyboard-focus indicators use a solid blue outline, including navigation/menu/language controls and table regions. Main-region focus is a programmatic reading destination, not an extra sequential Tab stop.

Other forms use the existing native dialogs, labelled controls and notices. Explicit saving/review/confirmation is unchanged: navigation does not autosave, approve or send a message. Save draft edits before leaving a page; do not treat a route change or focus change as proof of a completed write.

## Remaining limits

Owner/viewer navigation and selected first-owner/sign-in/compliance paths below are exercised, not every action/error/recovery state or optional team role. Provider-side manual outreach, browser extension/zoom/high-contrast settings, assistive-technology combinations, branded browsers and physical devices remain outside the checks. No live account or installed personal database is used or modified. Broader acceptance remains separate in phases049/073 and the personal readiness ledger.

The navigation uses the [W3C modal-dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) as guidance for contained, escapable focus and logical return focus, and [W3C bypass-blocks guidance](https://www.w3.org/WAI/WCAG22/Understanding/bypass-blocks.html) for the shortcut. Using these patterns is not itself an accessibility certificate. Report a problem with the route, language, viewport, focused control, exact keystrokes and redacted expected/actual behaviour.

## Keyboard first-owner setup, sign-in and compliance

Setup, sign-in and compliance share the same post-enable focus recovery rule: restore the connected submitting control only when focus fell to BODY in a foreground document. Focus moved to another control or window is never reclaimed. Refused setup and sign-in must retain or restore their submitting control in the actual browser checks, so correcting a password/token remains reachable with native keys. Six auth regressions supplement the seven compliance cases; exact latest runs remain in the ledger below.

On a fresh personal installation, Tab to the language selector and use native selection keys. Fill the operator setup token when shown, name, workspace, email and a password of at least12 characters; Tab to Create workspace and Enter. These are local application credentials, never your Simbi password. Required/minimum-length native validation focuses the invalid field without a request. A refused setup preserves fields for deliberate correction, not a claim that an owner was created. After setup, navigate to Settings (Open navigation on mobile), read the four policy/source/manual-send/stop-contact statements, select each with Space, then Enter on Record acknowledgement. Confirmation/choices are disabled during posting/readback, with localized pending text and synchronous repeat refusal. Completion restores a submitting control that lost focus to BODY only if the document still has focus and you did not move elsewhere. Rejection keeps the choices for an explicit retry; an uncertain response does not prove no commit. Sign out through the sidebar/drawer, then Tab through the local login form. Invalid required fields make no request; a rejected password preserves fields for correction.

## Keyboard-only personal record-keeping journey

`scripts/e2e-keyboard-workflow.mjs` extends the full existing suite with an English1440x1000 and Dutch390x844 owner journey. It starts with the harness's already authenticated, compliance-acknowledged fictional owner; it does not claim keyboard setup/sign-in/compliance acceptance or use Robert's account. All application controls are reached by actual sequential Tab/Shift+Tab, not a locator's programmatic focus. Earlier controls use backward Tab instead of assuming a browser-specific forward wrap after focus leaves the document. Enter/Space activates buttons and checks, keyboard text entry edits inputs, and Home/ArrowDown selects native options. On mobile, routes are reached through the native navigation drawer. The observer counts real key events and requires zero pointer-down events. Browser inspection/read-only authenticated export calls verify results; none creates fixture records on behalf of the interface.

The path creates and activates a campaign, manually adds an authorized-source fictional prospect, creates a deterministic template, prepares a draft, edits and explicitly saves it, completes all four review checks, and prepares one handoff. Unsaved text cannot be approved. It records **fictional uncertainty**, reopens that historical handoff and escapes with return focus; **Copy message, Open provider and Sent manually are never activated**. It then creates a review reminder through native date/time entry or the explicit text option described below, records a fictional reply, verifies the reminder is `cancelled` (not `done`), checks the campaign's report row and records a stop-contact restriction. Historical `replied` state remains after contact is stopped. Successful stop confirmation returns focus to the named Prospects table region because its former trigger is now disabled; cancellation returns to the original enabled button, and a rejected confirmation keeps its dialog and reason.

An empty campaign submission must focus the invalid required field without a server write; Escape from its creation dialog must restore the trigger. Each locale requires exactly twelve deliberate UI mutations and compares all eight pre-existing operational table arrays unchanged: campaigns, prospects, templates, drafts, handoffs, replies, reminders and suppressions. The separate navigation checks cover both viewport sizes in both languages.

The browser's native date/time control differs by OS and engine. The reminder form keeps native entry by default and offers **Enter date and time as text** (**Datum en tijd als tekst invoeren**). The text format is `YYYY-MM-DDTHH:mm`, for example `2027-11-02T07:58`, interpreted in the browser's local time zone and converted to UTC for storage. Calendar rollover (such as 30 February), year zero, offsets and nonexistent local wall times are rejected before writing; validation errors keep the dialog/value and focus Due. Uncertain server responses are separate and do not guarantee no write or Due focus. Switching mode or interface language preserves the entered text in this open form, not across closing/reloading. Ambiguous repeated daylight-saving times use JavaScript's local-time interpretation; this is not an explicit time-zone/fold selector.

The test first uses native segment arrows. When they leave an empty value, it selects the app's text-entry checkbox with Space, reaches Due with Tab and enters the documented fictional value. Both variants require complete validity and exact displayed-value/ISO/server-record readback; there is no DOM value assignment or assumed US date order. The fallback is an actual operator-visible path, not a test-only injection. This is bounded keyboard-operability proof, not identical native-picker UX across every platform.
